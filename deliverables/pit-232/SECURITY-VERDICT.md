# PIT-232 security verdict — tunnel-token intake, both doors

**Verdict: ADVERSE — 2 blocking findings.** The dashboard door (PIT-236) is close to shippable. The commissioning door (PIT-231) is not: its only authority check admits the UID of the browser that renders third-party web content, and neither validator pins the token to our Cloudflare account. Together those two facts let remote content attach a club's card to an attacker's tunnel.

Fixes route to Chief of Staff (owns PIT-229). I edited no implementation file. No real token appears anywhere below.

---

## Blocking findings

### B1 — Critical. A club card can be attached to an attacker-owned tunnel from web content rendered on the screen.
**Target:** `deploy/setup/wifi-startup.py:200-248`, `deploy/setup/wifi-privileged.py:71-97`, `deploy/setup/wifi-http-firewall.sh`

Four facts, each read in the tree, which compose:

1. **No account pinning.** `validate_token` checks shape only — `a` need merely be a non-empty string (`wifi-privileged.py:95`, `wifi-startup.py:81`, `app/bin/remote-access.js:113-116`). Any well-formed connector token from *any* Cloudflare account is accepted by all three validators.
2. **No authentication on the route.** `/remote-access` takes a password, no CSRF token, no `Origin` check and no `Content-Type` check — `do_POST` goes straight to `json.loads(self.rfile.read(size))` (`wifi-startup.py:226-248`).
3. **The permitted UID is the browser.** The only authority is the nftables reject on 8090 for every socket UID except `pitchtribe-kiosk` — and `pitchtribe-kiosk` is the user `pitchtribe-kiosk.service` runs Chromium as. That Chromium renders club-configured arbitrary URLs in iframes (`app/public/player/player.js:339-347`, `sandbox="allow-scripts allow-same-origin allow-forms"`). An iframe sandbox does not restrict `fetch()`.
4. **The listener is permanent, not commissioning-scoped.** `pitchtribe-wifi-startup.service` is `WantedBy=multi-user.target` with no stop condition, and on every Pi `WIFI_SETUP=1` (`deploy/install.sh:429`), so the route stays live for the card's whole life.

A cross-origin `fetch` to `http://127.0.0.1:8090/remote-access` with `Content-Type: text/plain` is a CORS *simple* request: no preflight, so the side effect lands even though the response is opaque to the caller. The attacker does not need to read the response — their own tunnel registering tells them it worked.

**Impact.** The attacker's own Zero Trust account owns the tunnel, so *they* define ingress, hostname and Access policy remotely. The card dials out, so no router change is needed and nothing on the card names their hostname. This is the exact inversion of the board's "a token alone publishes nothing" invariant: that invariant is a property of *whose account owns the tunnel*, and nothing currently constrains that.

**Remediation — both parts, they are independent:**
- Pin the account: reject any token whose `a` claim is not PitchTribe's Cloudflare account id. Add the constant to all three validators and extend `app/test/tunnel-token.test.js` to cover a foreign-account token.
- Add an origin control to the 8090 POST routes: require `Content-Type: application/json` **and** reject any request whose `Origin`/`Referer` is present and not `http://127.0.0.1:8090`, **and** require a one-time nonce minted into `/remote` and held in the broker's memory. Requiring the JSON content type is what forces a preflight that the server then must not answer.

### B2 — High. The commissioning door has no re-authentication at all; momentary physical access attaches the card to a tunnel.
**Target:** `deploy/setup/wifi-startup.py:226`

This is the Q3 asymmetry, and it is not defensible. The dashboard path re-verifies the dashboard password and is rate-limited (`app/lib/remote-access-routes.js:77-84`) exactly as the SSH and support paths do. The commissioning path has nothing. A person alone with the TV for thirty seconds — or anyone who reaches the kiosk UID by any route — provisions remote access with no secret they did not bring with them.

**Remediation.** Gate `/remote-access` on either the dashboard password (reuse `auth.verifyPassword`) or a commissioning window. The window needs no new state: `/run/pitchtribe-setup/active` already exists and is already referenced at `wifi-privileged.py:21`. Refuse `tunnel-enable` at the **broker** when that marker is absent, so the check sits on the privileged side.

**Related, same root cause:** there is a second door at the same authority with no HTTP layer to put a check on. `/run/pitchtribe-wifi-privileged.sock` is `0660 root:pitchtribe-wifi` and the kiosk user is in that group (`deploy/install.sh:474`), so anything running as the kiosk UID can call `tunnel-enable` directly, bypassing 8090 entirely. Whatever control B1 and B2 add has to live in `dispatch()`, not in `wifi-startup.py`, or it is decoration.

## Non-blocking findings

**F3 — Medium. Two doors, two locks, one credential: no mutual exclusion.** `wifi-privileged.py:196-200` takes an exclusive flock on `/run/pitchtribe-tunnel.lock` for the whole enable. `app/bin/remote-access.js` `tunnelEnable`/`tunnelDisable` never take it — the JS broker holds only its own lock under `STATE_DIR`. Concurrent enables race, and the JS rollback is the sharp edge: it restores a `previous` captured *before* the other writer landed, via `fs.writeFileSync` (non-atomic and symlink-following, reintroducing on rollback the half-credential window `tunnel_write`'s own comment forbids), or `fs.rmSync`es a credential the commissioning path just accepted. **Fix:** take `/run/pitchtribe-tunnel.lock` in the JS broker for the whole operation, and make the rollback write go through the same staged-rename as the forward write.

**F4 — Medium. The dashboard path's revocation detection is time-zone broken, so a rejected token can stay on disk.** `app/bin/remote-access.js` builds `since` as `o.now().toISOString().slice(0,19).replace('T',' ')` — a UTC wall-clock string — and hands it to `journalctl --since`, which reads a bare timestamp as **local** time (`systemd.time(7)`). The Python path gets this right with `time.strftime` (`wifi-privileged.py:204`). On a card set west of UTC the window starts in the future, the journal returns nothing, `Unauthorized` is never seen, and the club is told "Remote access is set up" while a rejected credential sits on disk with the unit enabled. At UTC+1 it fails the other way: the window is an hour too wide and can match a *previous* run's `Unauthorized`, rolling back a good token. The in-code comment calls this "close enough" — it isn't. **Fix:** `--since "@<epoch seconds>"`, which is unambiguous.

**F5 — Medium, hardening. cloudflared runs as root.** `deploy/setup/pitchtribe-tunnel.service` has no `User=` and no `CapabilityBoundingSet=`. The one process on the card terminating an internet-facing tunnel has UID 0 and the full bounding set; the existing `ProtectSystem=strict`/`NoNewPrivileges` do not change that. **Fix:** `User=cloudflared` with the EnvironmentFile `0600 cloudflared:cloudflared` (both writers chown to match), plus `CapabilityBoundingSet=` and `PrivateDevices=yes`. The port-20241 rule is on *output* and so is unaffected.

**F6 — Low. The image's ship-inert sweep only covers one door's territory.** `image/build.sh:259-260` greps `$MNT/etc`, `$MNT/root`, `$MNT/home` for `TUNNEL_TOKEN=ey…`. The dashboard door's plaintext staging file is `/var/lib/pitchtribe/remote-access-request.json`, in none of them. **Fix:** add `$MNT/var/lib/pitchtribe` and `$MNT/var/lib/pitchtribe-remote-access` to the sweep, plus an explicit assertion that `remote-access-request.json` is absent.

**F7 — Low. The dashboard path skips the cloudflared capability guard.** `wifi-privileged.py:100-113` refuses to write a credential at all if the installed cloudflared cannot take the token from its environment — the guard that keeps a future cloudflared from pushing us back to a token in argv. Since `install.sh` installs the package **unpinned** from Cloudflare's apt repo, that guard is load-bearing, and the dashboard path has no equivalent. **Fix:** port the check into `tunnelEnable` before the write.

**F8 — Low. "Leave empty to keep the current one" is not true.** `app/public/admin/admin.js` sends `token: token.value.trim() || undefined`; the empty-token guard only fires when the tunnel is *not* already on. So submitting the already-on card with an empty box reaches `validateTunnelToken(undefined)` and returns 400 "That is not a PitchTribe remote access token" — against a placeholder that just promised empty was fine. It matters beyond polish: it teaches clubs to re-paste a live token they did not need to handle. **Fix:** when `enabled` is true, no token is supplied and the tunnel is already enabled, treat it as a no-op.

**F9 — Low, subsumed by B1. `/remote-access/off` is unauthenticated too** (`wifi-startup.py:203,250`) — no body, no password, no origin check. Same reachability, so any web content on the screen can silently turn remote access off; the credential is unlinked, so recovery needs a fresh token from PitchTribe. B1's remediation closes it.

## The seven questions, each with a yes/no

**1. Token at rest — YES, correct.** `/etc/pitchtribe/tunnel.env`, `0600 root:root`, in a `0755 root:root` directory created by the installer (`deploy/install.sh:454`). No symlink/TOCTOU window on the forward path: `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW` mode 0600 to a random staging name in the same directory, fsync, `os.replace` (`wifi-privileged.py:147-167`). It reaches no backup: backups are an allowlist of `db.json` + `media/` only (`app/lib/backup.js:95-101`), and `/etc` is not in it. *Caveat:* the JS **rollback** write is not held to this standard — see F3.

**2. Token in cmdline — NO leak. Verified, not assumed.** `ExecStart=/usr/bin/cloudflared --no-autoupdate --metrics 127.0.0.1:20241 tunnel run` — no token on the line. `cloudflared service install <token>` is used by neither path, and `image/build.sh:232-237` asserts no `cloudflared*` unit exists on a flashed card, which is what actually proves the command was never run. No `subprocess`/`exec` call in either broker puts the token in argv — the only argv-bearing calls are `systemctl`, `journalctl` and `curl` with fixed arguments. The adjacent door is closed too, and it was a real one: cloudflared's metrics listener serves `/debug/pprof/heap` unauthenticated, and a heap profile of a process holding the token is a non-root read of that token — `wifi-http-firewall.sh` pins the port and rejects output to it for every UID except 0.

**3. Token in logs — NO leak found. I tried to make it leak.** All three validators return fixed help text and never interpolate the input; the base64/JSON exception text is deliberately swallowed (`wifi-privileged.py:91-94`) precisely because it would carry the pasted credential. The Python unix broker's `handle()` logs nothing at all. The JS broker's only warn on this path carries `reqAction()` — the action string, capped at 32 chars — not the body. `tunnel_rejected` and the JS journal poll return a boolean and never re-log journal text. `last.message` in the mirror is always a fixed string, and `tunnelView()` emits two booleans. cloudflared redacts the token in its own startup line. `app/test/remote-access-route.test.js` drives the routes over HTTP and asserts the token is in no response body or header; `app/test/remote-access.test.js` asserts it never reaches the mirror.

**4. Double validation — YES, at both boundaries, in both paths.** Commissioning: `wifi-startup.py:57` plus a verbatim copy at `wifi-privileged.py:71`, with `app/test/tunnel-token.test.js` failing on drift. Dashboard: the route validates (`remote-access-routes.js:104`) and the root broker validates again on the request it reads off disk (`remote-access.js` handleRequest, `tunnel-enable`). The dashboard's two call sites share one function, but they are two *processes* at different privilege and the dashboard user cannot write `/opt/pitchtribe`, so the property the standing rule at `wifi-privileged.py:60` protects does hold. One correction for the record: the comment at `app/bin/remote-access.js:86-87` says the validator is "duplicated verbatim (logic-wise) in app/lib/remote-access-routes.js". It is not — `routes.js` imports it. The comment should say so, because the next reader will otherwise go looking for a second copy to keep in sync.

**5. The authorization boundary — NO, not acceptable. Judgement, as asked.** The kiosk-UID nftables reject is a *process-isolation* control being asked to serve as an *authorization* control, and it cannot, because the UID it admits is the browser. Chromium's own sandbox protects the card from the content it renders; it does not stop that content opening a socket to 127.0.0.1. So the boundary admits exactly the attacker B1 describes, and the unix socket at `0660 root:pitchtribe-wifi` admits them a second way with no HTTP layer at all. An HTTP-unauthenticated local route that provisions an **outbound remote-access channel** from a **caller-supplied credential** with **no account pinning** is not acceptable behind that boundary alone. It would be acceptable behind that boundary *plus* account pinning *plus* a commissioning-window check on the privileged side — which is what B1 and B2 ask for.

**6. Ship-inert invariant — YES on the substance; the assertion is mostly real, with one soft spot and one gap.** A freshly built image carries no token, no credentials and no enabled connector service, and the checks that prove it are genuine: `build.sh:232-234` (units in `/etc`, `/lib`, `/usr/lib`), `:241` (`/etc/cloudflared`), `:247` (`/usr/local/etc/cloudflared`), `:250` (credentials by path), `:259` (credentials by **content**, so a renamed one is still caught), `:272` (`/etc/pitchtribe/tunnel.env`) each `die` on a real file and cannot pass vacuously. I also checked the checks cannot be silently skipped: `build.sh:202` dies if `chroot` cannot run at all, so everything below it is genuinely reached. **Soft spot:** `:236` and `:270` are `! chroot "$MNT" systemctl is-enabled … || die`, so *any* non-zero exit — including an unrelated failure — reads as "not enabled" and passes. There is no direct filesystem assertion on the enablement symlink. Add `[[ ! -e "$MNT/etc/systemd/system/multi-user.target.wants/pitchtribe-tunnel.service" ]]` beside it, which cannot be fooled. **Gap:** F6.

**7. Rollback — commissioning path YES, dashboard path NO.** `tunnel_restore` (`wifi-privileged.py:170-184`) disables the unit and unlinks when there was no previous credential, or atomically rewrites the previous one and restarts; a rejected token leaves neither a usable credential nor a running connector, and a club re-entering a bad token over a working one keeps the working one. The dashboard path has the same shape but depends on a revocation trigger that F4 breaks: on a card not set to UTC the `Unauthorized` search can never match, so a rejected token stays on disk with the unit enabled while the club is told it is set up. Both paths deliberately *keep* the credential when the connector simply has not registered inside the wait (25s / 30s) — that is the documented accept-before-Wi-Fi behaviour, not a rollback failure.

## The three cross-path questions

**A. Do both doors write the same credential to the same place with the same mode? YES — converged.** Both write `TUNNEL_TOKEN=<token>\n` to `/etc/pitchtribe/tunnel.env` at `0600 root:root` and enable `pitchtribe-tunnel.service`. The divergences are all in *how*, not *where*: no shared lock (F3), non-atomic rollback write (F3), no cloudflared capability guard (F7), broken `--since` (F4). None of them is a second storage scheme, which was the thing most likely to go wrong and did not.

**B. The plaintext-at-rest window on the dashboard path — bounded, and it reaches neither the mirror nor a backup.** `remote-access-request.json` is written `0600` by the dashboard user inside `DATA_DIR` at `0750 dashboard:dashboard` (`install.sh:157`), so only that user and root can read it; the portal user has its own `2770` subdirectory and cannot read the file. `pitchtribe-remote-access.path` fires on `PathChanged`, so pickup is normally sub-second, and `handleRequest` unlinks the file **on read, before deciding anything about it** (`remote-access.js:1236-1241`) — malformed and replayed ones included. If the path unit missed the write, the 5-minute `pitchtribe-support-expire.timer` run picks up strays, and anything past `REQUEST_MAX_AGE_MS` (15 min) is deleted and ignored. So the answer to "does it sit there until the next request overwrites it" is **no — it is unlinked as soon as the root helper reads it**, with a ~5 minute worst case.
It does **not** reach `remote-access-status.json`: `tunnelState()` returns `{enabled, connected}`, `tunnelView()` emits two booleans, every `last.message` is a fixed string, and there is a test asserting no token in the mirror. That matters given the mirror is dashboard-readable and already holds a live Connect code.
It does **not** reach a `DATA_DIR` backup artifact: backup contents are an allowlist of `db.json` + `media/` (`app/lib/backup.js:95-101`), so nothing from the root of `DATA_DIR` goes on a USB stick. The only residual is F6 — the *image* sweep does not look in `DATA_DIR`.

**C. Re-authentication parity — dashboard YES, commissioning NO, asymmetry not defensible.** See B2. The commissioning door does let someone with momentary physical access attach the card to a tunnel.

## And the board's invariant

**"A token alone publishes nothing" — YES, still holds; no local ingress was introduced.** `ExecStart` carries no `--url`, no `--config` and no hostname; there is no `config.yml` and no `/etc/cloudflared` on the card, and `build.sh:241-248` fails the build if either appears. Hostname, ingress and Access policy are remote. Not a blocking finding.
But note what B1 does to it: the invariant is a property of *whose account owns the tunnel*, and nothing pins that. With an attacker-supplied token the ingress is defined in the attacker's account and the card publishes whatever they choose. The invariant is only protective while the account is pinned — which is the strongest argument for B1's first remediation.
